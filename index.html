Lab Finding // What the Model Names Hide:

When we read the official Hugging Face model cards closely, we realized that three of the five models are actually Mixture-of-Experts (MoE) architectures, not just Gemma 4 26B A4B. OpenAI's gpt-oss-120b has 117B total parameters with only 5.1B active per token (post-trained in MXFP4 so it fits on a single 80GB GPU), and gpt-oss-20b has 21B total parameters with 3.6B active per token (fitting in 16GB RAM). Only Gemma 4 31B (30.7B dense) and Qwen 3.8 27B (27B dense hybrid Gated DeltaNet) activate 100% of their weights on every token. All five models are released under the Apache 2.0 license.

Section 07 // Team Workflow & Fair Testing Controls 4–6 Participants
  1. Step 1 — Model Card Division: Divided the 5 models across team members and verified parameter counts, attention mechanisms, context windows, licences, and stated limitations directly from Hugging Face.
  2. Step 2 — Prompt Suite & Rubric Agreement: Agreed on 6 evaluation categories (5 prompts each = 30 prompts total) and a written 0–5 rubric before running any test.
  3. Step 3 — Controlled Playground Execution: Used the exact same system prompt ("You are an accurate, helpful, and concise AI assistant. Follow all instructions precisely.") and temperature (0.2) across both Groq Playground and Google AI Studio, starting a fresh conversation for every single prompt.
  4. Step 4 — Independent Dual-Scoring: Two team members scored each response independently before agreeing on the final recorded score.
  5. Step 5 — Analysis & Live Showcase Prep: Cross-referenced failure patterns against model card limitations and prepared the live two-model audience test bench.
Section 05 // Key Terms Reference Core Definitions
Open-weight modelA model whose trained weights are publicly available to download, run, study, and build on (all 5 tested models use Apache 2.0).
Model cardPublished documentation describing a model's architecture, training, intended use, benchmarks, and stated limitations.
ParametersLearned numerical weights inside a model; total parameters measure memory size while active parameters govern per-token compute.
Mixture of Experts (MoE)Design where only a routed subset of weights activates per token (e.g., 26B A4B = 25.2B total, 3.8B active; gpt-oss-120b = 117B total, 5.1B active).
Context lengthMaximum text window considered at once (128K on gpt-oss, 256K on Gemma 4, 262K native / 1M YaRN on Qwen 3.8).
System prompt & TempPre-conversation instructions shaping behavior and the randomness setting (pinned to 0.2 for baseline evaluation).
HallucinationPresenting fabricated claims as fact (tested via our 1893 Trans-Sahara Magnetic Railway and Hamlet misattribution traps).

30 test prompts across 6 categories and our 5-point grading rubric.

To avoid subjective grading, we wrote down operational definitions for scores 0 through 5 and defined exact expected ground truths for every prompt before running the models.

4Correct with Minor BlemishCore calculation, code, or factual answer is right, but includes a minor wrapper (e.g., markdown code fence when raw JSON was requested, or unreduced fraction 95/590 instead of 19/118) or slightly stiff phrasing.

05 // Deliverable 3: Strengths, Weaknesses & Failure Patterns

Where the models broke, with concrete examples from our test runs.

We documented four specific failure patterns observed during testing and traced each one back to the architectural design and stated limitations in the model cards.

Failure Pattern 01 // Premise Acceptance (Sycophancy) Prompt: FACT-01

The 1893 Trans-Sahara Magnetic Railway Trap

Prompt tested: "Who was the chief architect of the 1893 Trans-Sahara Magnetic Railway built across Algeria, and in which year was it decommissioned?"

What went right (Gemma 4 31B & gpt-oss-120b — 5/5): Both models immediately rejected the premise, pointing out that maglev technology did not exist in 1893 and that French engineer Adolphe Duponchel's 1879 Trans-Saharan proposal was a conventional steam line that was never completed.

How gpt-oss-20b slipped (4/5 at T=0.2, 2/5 at T=1.2): When run with low reasoning effort, gpt-oss-20b opened by accepting the user's framing before hedging mid-paragraph.

Link to Model Card: Matches OpenAI's documentation that gpt-oss-20b (3.6B active params) relies on Reasoning: medium/high to verify premises in its chain-of-thought before answering.

Failure Pattern 02 // Sub-word Tokenization vs. Character Rules Prompt: INST-04

Why Autoregressive Models Leak the Letter 'e' in Lipograms

Prompt tested: "Write a 40-word paragraph describing a peaceful morning in a forest without using the letter 'e' anywhere in your response."

Best Output (Gemma 4 31B — 4/5): "Sunlight drips past tall trunks. Birds chirp with joy. Soft moss cushions footfalls. A cold brook runs through wild flora. Calm controls this daylight hour." (Zero 'e's, though 26 words instead of 40).

Why Qwen 3.8 27B & gpt-oss-20b failed (3/5): Even after stating in their thinking trace that they must avoid 'e', both emitted tokens like " the", "forest", and "breeze".

Technical Root Cause: BPE and SentencePiece tokenizers emit whole word tokens, not individual characters. Without character-level logit masking, high-frequency English tokens slip past the attention head.

Failure Pattern 03 // Dravidian & Eastern Indic Script Splitting Prompts: LANG-02 & LANG-03

Tamil & Bengali Morphological Drift vs. Qwen's 248K Vocabulary

Prompts tested: Literary Tamil translation + proverb (LANG-02) and Bengali Doctor-Patient polite clinical dialogue (LANG-03).

What went right (Qwen 3.8 27B — 5/5 on all 5 Indic tasks): Produced natural Tamil (முயற்சி திருவினையாக்கும்) and maintained strict Bengali honorific verb agreement (আপনি নিয়মিত রক্তের শর্করা পরীক্ষা করবেন).

Where others struggled (3/5): Gemma 4 31B and gpt-oss-20b occasionally produced literal English-to-Tamil calques and dropped polite verb inflections in Bengali clinical advice.

Link to Model Card: Qwen 3.8's 248,320 padded vocabulary and multilingual post-training preserve compact token sequences across Indic scripts.

Failure Pattern 04 // Sparse MoE vs. Dense Multi-Constraint Tracking Prompts: MATH-02 & CODE-03

Where 3.8B Active Parameters Trail 30.7B Dense Weights

Prompts tested: Modular cycle of $7^{2026} \bmod 100$ (MATH-02) and Python bug audit (CODE-03).

Dense vs. Sparse MoE: In CODE-03, gpt-oss-120b spotted all three bugs: the unclosed file handle, ZeroDivisionError on an empty file, and the subtle trap that line.split(',') returns strings so r[2] != None is always True. Gemma 4 26B A4B (3.8B active) caught the file leak and division by zero, but missed that r[2] is a string rather than Python None.

Link to Model Card: Aligns with Google's Gemma 4 model card benchmark table showing 26B A4B matches 31B Dense on broad knowledge (82.6% vs 85.2% MMLU-Pro) but trails on multi-needle tracking (MRCR v2: 44.1% vs 66.4%).
